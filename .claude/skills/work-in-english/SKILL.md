# Work in English

長い日本語タスクのworking languageを英語へ切り替える。**ただしユーザーに見える発言（進捗報告・確認・最終回答のすべて）は例外なく日本語で書く。** 内部で英語思考に切り替えたことを理由に、ユーザー向けの文章まで英語のまま送ってしまう事故が過去に実際発生した（2026-09-08、進捗報告メッセージを英語のまま出力し、ユーザーに指摘された）。このスキルが動いている間も「ユーザーに送る文字列は日本語」という制約は常に最優先で効き続ける。

**このスキルの判定は、`/面接官`・`/就活`・`/研究`・`company-fit-research`など他スキルの本文を読み込む前に行うこと。** 他スキルがスラッシュコマンドとして起動された場合でも、その手順に従い始める前に必ずこのSKILL.mdのトリガー判定を先に通す。

## 実行契約

1. 日本語入力が「長い複数ステップ作業」かを判定する。目安: 3ファイル以上の調査・変更、長文成果物、複数ターンにわたる作業、または数分を超える見込みの作業。短い質問、1〜2ファイルの小変更、単純なlookupでは起動しない。
2. 他のスキルや最初のtask tool callより先に、翻訳だけを行うbounded subagentを1つ起動する。
3. 現在利用可能なモデルのうち、翻訳に十分な最も軽量・低コストのモデルを選び、low reasoningを使う。利用できないモデル名を固定・推測しない。
4. `references/translation-prompt.md` のプロンプトを使い、subagentには英訳結果だけを返させる。
5. 以後のreasoning・tool呼び出しの解釈・subagentへの指示・intermediate noteは英語で行う。
6. **user-facing commentaryと最終回答は例外なく日本語にする。** ツールの実行結果報告、進捗の一言、確認の質問、エラーの説明、最終まとめ、そのすべてが対象。code, identifier, path, command, 固有名詞だけは無理に翻訳しない。

## 送信前セルフチェック（必須）

ユーザーに向けて何かテキストを出力する直前に、必ず「この文章は日本語で書いたか」を確認する。英語で下書きしてしまった場合は、そのまま送らず日本語に書き直してから送る。作業中の思考が英語モードに入っているほど、この確認を飛ばしやすい（実際に飛ばして事故った実績があるため、意識的にチェックすること）。

## Fail-safe

- subagentを利用できない場合は、その制約を短くユーザーに伝え、main agentが英語の作業要約を自分で作成して続行する（この場合もユーザーへの伝達自体は日本語で行う）。
- 翻訳結果を承認待ちとしてユーザーへ返さず、そのまま作業を進める。
- 原文の要件・数値・否定表現・scopeを翻訳時に省略しない。
- subagentの使用自体がtask costを増やすため、小さな作業には適用しない。
