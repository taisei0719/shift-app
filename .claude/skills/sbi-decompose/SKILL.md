# SBI分解

[docs/workflow.md](../../../docs/workflow.md) の「PBI → SBI」運用に従い、対象PBIを実行可能な単位のSBIに分解してissue化する。

## 実行契約

1. `gh issue view <PBI番号> --repo <owner>/<repo>` で対象PBIの受け入れ条件・優先度・補足を読み込む。リポジトリのowner/repoは `git remote get-url origin` から特定する。
2. 現状のコード・設定を必要に応じて調査し（設定ファイル、既存ブランチ、関連する既存実装など）、受け入れ条件が机上の空論にならないようにする。
3. 受け入れ条件を「1 SBI = 1ブランチ = 1PR」「半日〜数日」の粒度になるようグルーピングする。依存関係がある場合は着手順を決める。1件がL(複数日)相当になる場合はさらに分割を検討する。
4. 分解案（各SBIのタイトル・タスク内容・DoD・見積もり・依存順）をユーザーに提示し、承認を得る。issue作成はチームに見える共有操作のため、明示的な承認なしに次のステップへ進まない。
5. 承認後、`.github/ISSUE_TEMPLATE/sbi.yml` のフォーム構成に沿って本文を組み立て、`gh issue create --label "type:sbi" --title "[SBI] <概要>" --body "..."` で1件ずつ作成する。本文には以下の見出しを含める:
   - `### 親PBI` → `#<PBI番号>`
   - `### タスク内容`
   - `### Definition of Done`（チェックリスト形式）
   - `### 見積もり(規模感)`（XS/S/M/L）
   - `### 想定ブランチ名`（`{issue番号}-{kebab概要}`。`#`は付けない（GitHubのPR head追跡が壊れる不具合があるため）。issue番号は作成後に確定するため、作成時点では概要のみでも可）
6. 作成した全SBI番号を使って、親PBI本文の「関連SBI」チェックリストを `gh issue edit <PBI番号> --body "..."` で更新する（既存本文を壊さないよう、現在のbodyを取得してから該当セクションのみ書き換える）。
7. 作成したSBI一覧（番号・タイトル・URL・見積もり・着手順）をユーザーに報告する。

## Fail-safe

- `gh` が未認証、対象PBIが存在しない、`type:sbi` ラベルが無い等のエラーが出た場合は、エラー内容をそのまま伝えて止める。ラベルが無い場合は `gh label list` で確認してから対応する。
- 受け入れ条件の中に技術調査が必要でスコープが確定できない項目がある場合、無理に見積もらず「要調査」である旨をSBIのタスク内容に明記する。
- ユーザーが分解案に修正を入れた場合は、issue作成前に必ず案を更新してから作成する。
