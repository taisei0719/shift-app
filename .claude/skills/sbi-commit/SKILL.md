# SBIコミット

実装は大きく溜め込まず、小さい区切りごとに立ち止まってコミットする。「実装→コミット→次の実装→コミット」を基本の往復とし、複数の変更をまとめて一度にコミットしない。

## 実行契約

1. `git status` / `git diff` で変更範囲を確認する。関連しない変更が混ざっていれば、単位ごとに分けてstageする。
2. コミット前に、実装内容を報告する:
   - **ファイルごと**に何を追加・変更したか（新規作成ファイルは役割、既存ファイルは変更点を簡潔に）
   - その区切り（SBI全体、または今回コミットする単位）で**どんな機能が実装されたか**を1〜数文でまとめる
   これは「コミットしてよいですか」だけで済ませず、必ず先に提示する。
3. コミットメッセージは `#{issue番号} {type}: {説明}` 形式で書く（[docs/workflow.md](../../../docs/workflow.md) 5章参照）。
   - `{issue番号}`: 紐づくSBI issue番号
   - `{type}`: `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `style` / `perf`
4. コミットしたらそこで止まる。push・PR作成には進まない。次の作業（追加実装か、push/PR作成か）はユーザーの指示を待つ。
5. 実装がすべて終わっていなくても、意味のある単位（1つの受け入れ条件を満たした、リファクタが一区切りついた等）に達していれば、ここでコミットしてよいか一言確認してから進めてよい（手順2の報告とあわせて）。

## Fail-safe

- pre-commit/CIフックが失敗した場合は `--no-verify` で回避せず、原因を直してから再コミットする。
- .env等の機密情報が疑われるファイルが混ざっていないか、stage前に `git status` の結果を確認する。
